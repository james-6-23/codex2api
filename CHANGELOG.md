# Changelog

## v2.8.9 - 2026-09-01

### Features

- **Account export and import can carry proxy bindings, making a pool migratable in one piece.** Export accepts `include_proxy=1` to append `proxy_url`, `proxy_label`, and `proxy_enabled`; import accepts `import_proxy` to adopt the file-carried proxy and register it into the proxy table. Proxies are written and synced into the in-memory pool *before* any account row is written, and a failed reload aborts the whole import — reversing that order would pin accounts to a URL that is registered as managed but not yet enabled, which fail-closes them out of scheduling. Invalid entries are skipped and fall back to the form proxy, more than 500 proxies registers none at all, pre-existing rows are never revived by `ON CONFLICT DO NOTHING`, source-disabled proxies import as enabled with an explicit warning rather than silently killing every account bound to them, and new rows are labeled `imported-<YYYYMMDD-HHmm>` for batch cleanup. A file-carried proxy fills an empty binding but never overwrites an existing one, since the target may already have a deliberate assignment; a form-entered proxy keeps its existing overwrite semantics. Grok reads the proxy from raw file JSON because its credential parser has no proxy fields, and preserves the existing binding on the recycle-bin revive path. Antigravity already honored the file-carried proxy but never registered it, leaving accounts bound to URLs the proxy page and rotation could not see; its switch therefore only controls table registration, and its export keeps `include_proxy` defaulting on because it has always emitted `proxy_url`. Verified end to end against PostgreSQL, including `ON CONFLICT` idempotency, preserve-on-revive, and the export → import → export round trip.
- **Antigravity accounts are now admitted through `/v1/chat/completions` and `/v1/messages` (#595, reported by @maikaken).** Both endpoints already translate their inbound body into a Responses payload, which is exactly what the `v1internal` adapter consumes, so all three transports now share one admission gate and one adapter instead of excluding the channel outright. The Responses-to-Chat return translation only consumes SSE, so the upstream call is always streamed and non-streaming clients are aggregated gateway-side. An upstream 401 on an OAuth account refreshes the token and retries the same account once, matching `/v1/responses`, instead of discarding a usable account as an auth failure.

### Fixes

- **Antigravity function tools are bridged by default instead of being dropped (#595).** Silently discarding the tools was worse than not supporting them: the upstream still received the system instruction describing those tools, answered with a call it was never allowed to declare, and terminated the turn as `MALFORMED_FUNCTION_CALL`. Responses function tools now map to Gemini `functionDeclarations`, and previous `reasoning` items echoed back as conversation history are skipped rather than rejected, so multi-turn tool conversations survive. Built-in Codex tools with no `v1internal` equivalent are still ignored, and `ANTIGRAVITY_FUNCTION_TOOLS_ENABLED=false` pins the bridge off for diagnostics.
- **Re-importing a deleted Grok account no longer dead-ends on its own recycle-bin record (#602, reported by @a1073185067).** The credential identity fence includes recycled accounts by design, so re-importing a previously deleted `refresh_token` failed with "credential identity already exists (account N)" while the account list showed nothing — no visible way out. SSO, refresh-token, and `auth.json` file imports now merge the credentials into the holder and revive it from the recycle bin; a manual add that collides returns a 409 naming the holder and pointing at the recycle bin. The reauthorization overlay no longer falls back to the subject as an email, so a token without an email claim cannot clobber the account's real address, and import results carry `updated`/`revived` flags so the detail dialog can explain why no new account appeared.
- **Codex sibling subagents no longer preempt each other on a shared WebSocket connection.** A Codex session tree shares one session-id while each parent and child agent carries its own thread-id, so independent subagents were collapsed onto a single transport lane and cancelled one another. Genuine child threads now get their own local connection lane, derived from raw downstream identity before any fingerprint convergence — fingerprint policy governs what the upstream sees, not whether independent local streams must serialize. When convergence is off or device-scoped, the client's self-reported Thread-Id is preserved instead of being flattened into a single-thread shape.
- **The Messages-to-Responses streaming adapter no longer emits misaligned or partial output items.** Empty text and thinking blocks reserved an `output_index` but were skipped in the terminal object, so accumulators and the final response disagreed. Start-only blocks are now emitted before done, a second `content_block_start` without a stop begins a fresh message lifecycle instead of manufacturing done events for the abandoned item, a `content_block_stop` arriving mid tool-call JSON after a `max_tokens` cut is never announced as completed, and `input_json_delta` is treated as authoritative over the provisional start input.
- **Synthetic Responses objects keep a stable `created_at` across conversions.** Reading a complete upstream body can block until generation finishes, so the creation time is now frozen before that work starts, and stream-break frames reuse the timestamp observed on the stream instead of stamping the moment of failure.
- **Spark 429s stay scoped to the Spark model, and image capability cooldowns require structured evidence.** Spark has an independent quota window, so its `usage_limit` metadata must not rewrite the account plan or the main 5h/7d snapshots; only explicit quota evidence drives the Spark window, while transient rejections keep the ordinary short model cooldown. Separately, a `response.completed` frame containing plain model text is prompt-dependent and no longer persists an image-generation capability cooldown on the account/model pair.

## v2.8.8 - 2026-08-31

### Fixes

- **WebSocket connections now accept `socks5h://` proxies.** Managed proxy validation and HTTP probes already accepted `socks5h`, but the Gorilla WebSocket dialer only recognizes `socks5`, so forced-WebSocket requests failed locally with `proxy: unknown scheme: socks5h` even when the same proxy tested healthy. The WebSocket path now reuses the lenient proxy parser and normalizes only the connection-local scheme to `socks5`, preserving credentials and proxy-side DNS resolution; a fake SOCKS5 regression test verifies the domain-form CONNECT target, and a PostgreSQL + Redis 2004 live request confirmed the bound `socks5h` proxy completes a real upstream WebSocket response.

The invite page batch-checks both pasted emails and account-list candidates, keeps previously invited accounts visible with a disabled “Invited” marker, blocks manual duplicates, and clears the recipient input only after a successful send.

## v2.8.6 - 2026-08-31

### Features

- **New Codex account imports can open an invite-earnings guide and reuse a richer invite workspace.** The default-on guide probes at most 50 eligible OAuth accounts through the existing adaptive import-probe gate, polls cached eligibility without delaying the import response, ranks accounts by referrer-only reward value and remaining rewarded sends, and can allocate a limited recipient-email budget to the highest-value accounts first. Successful eligibility and 90-day tracking observations are cached in memory/Redis and durable credential-generation-fenced snapshots so repeated page visits do not hammer the Cloudflare-protected endpoints; challenges and failures are never persisted as ineligibility. The invite page now shows monthly send capacity separately from 90-day sent/accepted/pending counts, supports explicitly probing another 50 accounts with tracking, and can select deduplicated recipient emails from the Codex account list while excluding the sender. Administrators can disable the post-import guide from Settings or the modal without disabling the invite page itself.
- **Grok reasoning streams gain an opt-in quality guard for degraded accounts (#570 and #587, reported by @a1073185067).** For streaming Grok 4+ requests whose reasoning is actually observable, the gateway can hold a bounded prefix and discard an answer with enough visible output but no real thinking delta, encrypted reasoning, or signature evidence, then rotate accounts before anything reaches the client. The guard defaults off and skips explicit no-reasoning requests, compaction turns, short replies, unobservable native streams, and replay-unsafe hosted tools. Defaults are six quality attempts, a 30-second hold ceiling, fail-closed exhaustion, and a 12-hour first-offense cooldown; a second offense after cooldown disables the account, while later healthy reasoning resets the penalty ladder. Empty streams use a separate 15-minute cooldown, usage from discarded attempts is retained, and fail-open remains available as an operator-selected escape hatch.
- **Response-context cache writes can be limited to downstream keys that actually use `previous_response_id`.** The new `on_demand` policy grants each API-key owner a sliding one-hour write window after any continuation lookup, then writes both local and Redis context only for that owner; deployments whose clients always resend full context can therefore eliminate unused tool-context write amplification. The compatibility default remains `always`, invalid values are rejected, the policy is persisted independently with the existing response-cache generation, and cache telemetry exposes skipped writes plus the number of currently eligible owners.
- **Database-backed API keys can be enabled or disabled without deleting or rotating them.** Existing and newly created rows migrate as enabled, the admin table exposes a guarded enable/disable action and a distinct disabled status, and a disabled key is rejected by the normal authentication middleware with a masked security-audit event. Environment-configured keys retain their existing behavior.
- **WebSocket connection logs expose the real upstream `permessage-deflate` negotiation result (#586, reported by @huyachigege).** The dialer already offered compression; the gateway now records whether the upstream accepted it, including negotiated parameters, once per distinct outcome bitmask so direct and relay routes remain observable without producing one log line per connection. Real-upstream verification observed `server_no_context_takeover` and `client_no_context_takeover` negotiation.

### Fixes

- **The experimental server-side Plus-to-Pro subscription-upgrade surface is removed (PR #591 by @Cd1s).** The undocumented ChatGPT Web billing path was frequently blocked by Cloudflare challenges and a successful payment could invalidate the OAuth credential family, making a server-side paid mutation too unreliable to keep. Quote, payment, verification and operation-history routes are no longer registered; their admin UI, settings switch, environment default, proxy client and documentation are removed, while unrelated read-only subscription-expiry synchronization remains. Existing installations keep any old nullable setting column and operation-journal table because the migration deliberately performs no destructive schema cleanup.
- **Antigravity sync failures preserve actionable Google account-recovery details.** Structured `VALIDATION_REQUIRED` and `TOS_VIOLATION` responses are parsed from the untruncated upstream body, rendered as persistent verification or Terms-of-Service diagnostics instead of generic transient warnings, and surface the supplied verification or appeal URL as a safe clickable action. Ordinary transient failures still keep their upstream message, partial quota sync remains non-fatal, and raw JSON blobs or truncated one-time links are no longer dumped into the UI.

## v2.8.5 - 2026-08-27

### Features

- **Administrators can run guarded Plus-to-Pro subscription upgrades (PR #583 by @Cd1s, disabled by default).** Quote-first admin APIs enforce exact amount caps, keep a durable idempotency journal across the paid path, submit payment at most once per account, and expose reauthentication readiness before any money moves. Hardening on top of the contribution: the enable switch moves out of the startup environment into the admin settings page (a stored value is authoritative and the environment can no longer re-enable it), the per-account lock is taken before quote resolution so two requests sharing a quote but carrying different idempotency keys cannot double-pay, post-payment journal writes and verification detach from the request context so a client disconnect cannot strand the one record that matters, only 401 counts as credential invalidation (a Cloudflare 403 falls to `verification_pending` instead of a misleading "payment accepted, credentials revoked"), a partial unique index on submitting rows guards against cross-instance double submission, the minor-unit factor is derived from the currency so zero-decimal currencies such as JPY are not displayed 100x off, and a strictly read-only `/verify` reconciliation endpoint releases operations stranded mid-submission without ever repeating the paid POST.
- **Antigravity OAuth clients are managed from the system settings page.** Clients persist in a dedicated settings column read and written by its own small UPDATE, so an unrelated settings save can never clobber them. Environment-provided clients stay read-only and win on key collision, the built-in official Desktop client remains the fallback when nothing is configured, client secrets are never echoed back to the browser, and submitting an empty secret keeps the stored one.

### Fixes

- **Active sessions no longer rotate accounts mid-conversation, preserving the upstream prompt cache (#584, reported by @a1073185067).** Bounded session affinity forced a re-pick after 50 requests or 5 minutes since first bind — and the clock never reset while the conversation stayed active — so long agent tasks lost their bound account mid-task and every follow-up message after a completed task landed on a different account, re-ingesting the entire context at the uncached rate. Rotation now happens only when the bound account turns unhealthy or the session has been idle past `CODEX_SESSION_AFFINITY_IDLE_ESCAPE` (default 10 minutes), by which point the upstream prompt cache has already expired and rotation is free. Sticky and continuation hits refresh the idle clock, and capacity-spillover borrows are logged since they imply an expected cache miss for that single request.

## v2.8.4 - 2026-08-27

### Features

- **Upstream failures can opt into configurable continuous full-attempt recovery (PR #549 by @Establishmentarian).** The default-off selective mode matches transport failures, 429, 4xx/5xx classes, stream failures, `response.failed`, context errors, exact HTTP statuses, or exact upstream error codes. A separate default-off catch-all super switch retries genuine upstream failures without relying on a known-code list, including unknown future failures and permanent quota, authentication, balance, invalid-request, or non-CYB structured safety-policy errors. An explicit upstream `cyber_policy` is always a hard stop: it is never replayed on another account and retains its signed decision, conversation lock, and verified-user cooldown. Streaming attempts are retained privately and discarded on retryable failure; only an HTTP 200 response with a normal protocol terminal is replayed to the client, while SSE comments or Responses WebSocket Ping keep the downstream alive. This intentionally trades real-time token delivery for transparent mid-stream recovery. Account rotation uses valid `Retry-After`, configured delay, and capped exponential backoff with jitter. Client cancellation, local validation/policy/spool failures, downstream write failure, WebSocket disconnects, and explicit CYB stop immediately. The UI warns that deterministic failures and media creation can repeatedly consume tokens, requests, balance, account quota, memory, disk, and duplicate charges.
- **Continuous retry now has a request wall-clock ceiling.** `max_duration_seconds` defaults to 600 seconds and starts only when a request first enters the unlimited retry budget; later attempts cannot reset it. Expiry cancels drainable upstream work immediately, releases request concurrency, returns the latest upstream failure through HTTP/SSE/WebSocket (falling back to `upstream_timeout` when none exists), and closes Responses WebSocket turns with 1013. Non-streaming Grok media keeps its JSON protocol and emits best-effort HTTP 102 Processing informational heartbeats during active retry waits and upstream I/O without committing the final status; intermediaries may still drop 1xx, so the wall-clock ceiling remains authoritative.
- **Antigravity becomes a dedicated Google upstream channel with OAuth account management, browser authorization, credential import, scheduling, scoped models, API-key channel restrictions, usage attribution, and an account UI.** OAuth traffic uses the Cloud Code `v1internal` adapter and can refresh once after an upstream 401. Antigravity account groups and model backing remain isolated from Codex and Grok.
- **Google API Key accounts can declare Gemini models and model mappings and target the Generative Language `v1beta/interactions` endpoint.** This path is explicitly experimental: local tests cover endpoint/header/body construction, but the complete Google request, SSE/JSON response, tool-call, usage, and error wire contract still requires authoritative real-upstream verification.
- **Antigravity gains dedicated admin credential export and a sanitized management plane.** One account downloads as secret-bearing JSON and multiple accounts as a sanitized-member ZIP; state reads are side-effect free, OAuth sync refreshes Google control-plane snapshots, API-key sync remains explicitly local/unverified, and bounded capability probes persist generation-fenced protocol observations.
- **An opt-in real Google Interactions integration test now exercises the production executor.** It is gated by `ANTIGRAVITY_INTERACTIONS_TEST_API_KEY`, supports safe model/input/SSE controls, validates native status/content types and bounded envelopes, and skips explicitly when no key is supplied. Production certification still requires a successful real run.
- **The routing scheduler gains a staged engine rollout: `legacy`, `shadow`, and fully `indexed` selection.** Indexed mode selects from priority/health buckets with sparse API-key sub-pools, deterministic affinity offsets, and event-driven availability waits; shadow mode keeps legacy authoritative while sampling one in 64 requests for candidate-parity comparison. `CODEX_SCHEDULER_ENGINE` pins an instance for a canary or emergency rollback, `FAST_SCHEDULER_ENABLED=true` remains a compatibility alias for indexed, and `/api/admin/ops/overview` reports the active engine, indexed/legacy selections, scan volume, event waiters, routing-cache state, shadow parity, and outbox lag. Grok account state updates move to scheduled maintenance jobs so probe results land without waiting on request traffic.
- **Sessions can briefly hold their account slot after a successful request (PR #555 by @ekti123456).** The default-off session slot buffer reserves the concurrency slot for a configurable duration (default 10 seconds) after a turn completes, so a fast follow-up turn keeps its account under concurrency pressure instead of losing the slot to an unrelated request; occupancy displays count buffered slots as occupied.
- **The model pricing page previews billing for every model, exact aliases get independent pricing controls, and accounts show upstream API balances and per-model average first-token latency (PR #578 by @ifThink404).** The pricing page renders a per-model cost preview from the effective layered price, exact alias entries (such as `codex-auto-review`) become independently editable, the accounts page can display each account's upstream API balance behind a badge switch, today's usage details add a per-model average first-token duration, and the frontend recovers cleanly from stale chunks after a redeploy by clearing runtime caches before retrying. Unsigned CY locks are also scoped properly: risk-profile listings gain upstream-CY-only and activity-state filters, and a lock created by a local rule is no longer presented as an upstream CYB lock.
- **A 5-hour window auto-activation keeps Team accounts rolling (default off).** Some Team accounts do not start the next 5-hour window until a real request is sent, so a pool that went quiet over a reset wastes the whole window. When enabled, the gateway sends one minimal request after a detected reset for accounts whose upstream usage still reports a 5h window and reset time. This consumes a small amount of quota and stays disabled by default.
- **Codex HTTP request bodies are zstd-compressed like the real Codex CLI (default on).** The real client compresses `/responses` requests by default, so an uncompressed gateway stood out; a settings switch can turn it off.
- **Proxy connectivity tests understand SOCKS5 and IPv6.** Probes now speak the SOCKS5 handshake directly against IPv4 and IPv6 targets with stricter response parsing and clean fallback for unreachable targets.
- **Official usage USD totals cover every retained snapshot instead of only the last seven days, and model-list reads are size-capped.** `official_usd_7d` becomes `official_usd` and includes older snapshots, so the account page total matches the persisted settlement history; a new `models_list_read_max_bytes` limit rejects oversized upstream model list responses. Codex AT accounts are excluded from official usage statistics and backfill, and the official usage tab only appears for eligible accounts.
- **`gpt-reserve` joins the built-in model list (PR #562 by @bGlzdGRlcg).**

### Fixes

- **Status-less `ErrUpstream(0, ..., cause)` transport failures keep their transport classification after continuous retry landed.** Executors wrap `http.Client.Do` EOF/reset as a non-legacy-retryable structured error; the classifier now unwraps that cause so sticky same-account transport retries still bind the original relay account.
- **Antigravity API Key accounts no longer enter OAuth unauthorized-refresh recovery, and API Key rotation rejects a duplicate credential family.** Account responses expose only the credential kind and never return the key itself.
- **The OAuth Responses-to-Gemini converter rejects empty unsupported input, converts OpenAI function declarations into Gemini `functionDeclarations`, and rejects unsupported tool types instead of forwarding malformed objects.**
- **Long Responses streams stay alive through downstream idle timeouts (PR #561 by @dundunge).** SSE keepalive comments are emitted toward the client during long upstream silences, so reverse proxies and clients no longer cut a healthy long-running stream and log it as a 499.
- **Cross-channel reasoning history no longer 400s on Codex (#565, reported by @a1073185067).** Planning on grok-4.6 and then switching to gpt-5.6 replayed Grok-produced reasoning items into Codex, which rejects foreign encrypted content and reasoning `status` fields. Response preparation now drops reasoning items whose encrypted content does not carry the Codex prefix and strips `status` from the ones it keeps.
- **Grok tool schemas with non-object roots are normalized, and string-form upstream error bodies surface (PR #580 by @ifThink404).** Union roots (`anyOf`/`oneOf`/`allOf`), boolean schemas, and `type` arrays are collapsed into the object root Grok requires instead of dying on the upstream 400. Follow-ups close the remaining shapes: merged union roots preserve sibling keys such as `$defs` so `$ref` pointers stay resolvable, same-name properties across branches nest into `anyOf`/`allOf` instead of first-wins merging (a `const`-discriminated union no longer makes later branches uncallable), bare local `$ref` branches are resolved before classification with a cycle-safe depth cap, and `type:["object","null"]` roots get the same required-relaxation as the equivalent `anyOf`-null form. Reserved-name renames (`tool_search` → `tool_search_fn`) now also apply to history `function_call` items, so a genuinely user-declared reserved name no longer diverges between its declaration and its call history from the second turn on.
- **Capacity spillover no longer steals a session's durable binding, and restored Grok tool-call IDs match their type.** When the slot buffer spills a busy session onto a sibling account, the original binding is preserved for later turns instead of being overwritten — while a filter-rejected account still migrates the binding as before. Relay `fc_*` item IDs restored as `custom_tool_call` or `tool_search_call` are re-prefixed (`ctc_`/`tsc_`) so strict Responses validators accept the replayed history.
- **Exact alias pricing keeps the documented custom > synced order and normalized key lookups (follow-ups to PR #578).** A synced alias entry no longer silently overrides an admin-entered custom canonical price; alias fields now layer over the effective canonical price instead of falling back to code defaults; and underscore or space spellings resolve to the stored hyphenated key. Traditional Chinese strings for the new pricing preview and first-token labels are backfilled.
- **The prompt-guard fingerprint replay check stays off the hot path and can actually match every endpoint (follow-ups to PR #578).** A global existence gate skips fingerprint envelope construction entirely while no active fingerprint lock exists (cached with a 10-second TTL), and the real endpoint and model are threaded into fingerprint derivation so cooldown locks created from images or search requests are no longer unmatchable. CY attribution also honors an explicitly configured Moderations review adapter instead of sending Chat Completions to it.
- **codex-local conversation locks can be found, unlocked, and audited again (PR #573 by @zzzhouuu).** The lock path hashed the session through the fallback-signal fingerprint chain while the unbound audit path hashed only the raw session ID, so the resulting `session_hash` values never matched: the risk profile could not attach the lock and the administrator could not unlock it. Both paths now share one fingerprint chain (covering `Session-ID` and `X-Codex-Window-Id` fallback identities) in the existing lock-table format. The local audit view also includes local blocks that were already reviewed by the external model, log search matches persisted session hashes, and local log cleanup is scoped to `source=local_filter` so other audit sections stay intact.
- **Spark admission honors `DispatchPaused`.** The Spark scheduler snapshot only consulted lock-protected state, so an account paused by an operator or by the Codex overload breaker kept receiving Spark traffic while standard traffic skipped it.
- **The payload-rule model mapping dropdown includes the `max` reasoning effort (#575, reported by @jyeric).**
- **The self-service account review entry no longer vanishes (#576, reported by @ExoticSkywing).** The pending-review panel stayed hidden on empty or stale list snapshots, so admins could not find `/account-portal` submissions; the panel now stays visible and the account list cache is invalidated on submit.
- **CI stays green honestly.** The admin race shard is split alphabetically to stop 12-minute test timeouts, and a flaky audit-queue drain assertion waits for the workers' completion signal instead of racing close's bounded early return.

### Security

- **Antigravity documentation now calls out plaintext API Key persistence, database/admin protection requirements, Google terms and suspension risk, preview pricing uncertainty, and the experimental Interactions contract.**
- **Antigravity credential downloads are admin-authenticated attachment responses with no-store/no-cache and nosniff headers.** Filenames and ZIP members are sanitized, while ordinary list/state responses remain secret-free.
- **Custom balance query URLs are restricted to the account's base URL host.** The balance probe sends the account's stored API key (`Authorization: Bearer`) and custom headers — a key that is designed to never reach the browser — so accepting an arbitrary absolute URL was both a key-exfiltration channel and an SSRF probe surface. Absolute URLs must now match the base URL host and must not carry userinfo; relative paths are unchanged, and a cross-host URL is rejected before any request leaves the gateway.

## v2.8.3 - 2026-08-21

### Features

- **Grok accounts can expose exact GPT-compatible aliases across the three normal HTTP text APIs (PR #547 by @Establishmentarian).** The Grok account editor now manages per-account mappings such as `gpt-5.5` to `grok-4.5`; routing validates each target against the account's visible catalog, conservative pre-sync defaults, and any explicit whitelist, and scoped model discovery advertises only routeable aliases. Responses, Chat Completions, and Messages share the mapping path, including the existing Codex function/namespace/custom/deferred-tool and `tool_search` bridge. Responses WebSocket and `/responses/compact` remain excluded, and provider-hosted tools still depend on the concrete Grok backend.
- **Spark usage is tracked independently of the account's ordinary 5h/7d windows.** Account responses and snapshots carry their own Spark usage percentage and reset time, and dispatch reads the Spark counters rather than inferring them from the standard windows, so a Spark-eligible request is no longer admitted or rejected on the wrong budget.
- **Liveness fails after a sustained account-store lock stall.** The non-blocking `/health` used to keep a deadlocked instance in service forever: the previous blocking handler would hang on the store lock, time out the container healthcheck and get the process recycled — an accidental but real self-healing valve that the `TryRLock` rework removed. A single failed `TryRLock` is still ordinary contention and returns 200, but when every probe fails continuously for 30 seconds `/health` returns 503 with `status=unavailable` and `blocked_seconds`, so orchestrator healthchecks recycle the instance without flapping under transient load.
- **Session, thread and window identifiers are derived as UUIDv7.** The identifiers are now time-ordered and deterministically derived from a seed plus timestamp instead of random v4 values, which keeps them unique while making a client session traceable in order. Installation identifiers stay v4.

### Fixes

- **The account store and the fast scheduler could deadlock the whole gateway (PR #553 by @ImogeneOctaviap794).** The two components could take their locks in opposite orders: request dispatch held `FastScheduler.mu` and then reached `Store.mu` through the egress filter's proxy resolution, while account add/remove held `Store.mu` and then called into the scheduler. A second, independent deadlock existed in the fallback, lazy, candidate-check and fresh-affinity paths, which ran account filters while already holding `Store.mu.RLock` — and Go's `RWMutex` blocks new readers once a writer is waiting, so a goroutine could end up waiting on its own nested `RLock`. Under load this froze every request that needed the account store, while static files and lightweight health checks kept returning 200, which made the process look healthy and prevented automatic recovery. Account-set mutations are now serialized by a dedicated mutex, `Store.mu` only covers the account slice and ID index, scheduler updates happen after that lock is released, and every filter runs against an account snapshot taken outside the read lock. Seven deterministic regression tests cover both lock classes.
- **A top-level envelope `type` field reached HTTP upstreams and produced 400s (#548, reported by @viktorcao).** After a Responses WebSocket connection hit a 1009 and fell back to HTTP, the request still carried the WebSocket envelope's top-level `type`, which the HTTP upstream rejects. The field is now stripped on every HTTP path — including the WebSocket fallback, continuation replays and forced-HTTP requests such as image generation and Agent Identity accounts — while nested `type` values are preserved.
- **`response.incomplete` is treated as a terminal state.** Upstream sends `response.incomplete`, not `response.completed`, when a request hits `max_output_tokens`, and that event still carries the full output and usage. Every terminal check only matched completed/failed, so an ordinary truncation was classified as a stream break: the gateway appended a synthetic failure terminal, discarded the real usage in favour of an estimate, and penalised the account with a 598. The damage was worst on `/v1/messages`, where the Anthropic translator had no case for the event at all.
- **Compaction triggers are normalized to the final input item, including a direct trigger object (PR #546 and PR #550 by @ImogeneOctaviap794).** Upstream rejects a `compaction_trigger` followed by any other input item. The gateway now keeps at most one direct trigger and moves it behind every history, message and tool item. A top-level `input: {"type":"compaction_trigger"}` object — which the request classifier already treated as a compact request — is wrapped into the same one-item array shape instead of being forwarded as an object, and non-canonical trigger type spellings are rewritten to the canonical wire value.
- **CYB conversation locks are auditable, and a Chinese credential-theft false positive is fixed (PR #552 by @ifThink404).** Risk profiles that are actively locked or cooling down are prioritized before pagination and can be filtered on their own, lock details expose the audit reference and decision id with a deep link to the original review log, and a lock created by a local terminal rule is no longer described as an upstream CYB lock. The `credential_theft` pattern no longer matches across separate Chinese clauses, so a benign request such as generating a login page and an export page is not treated as credential exfiltration; a follow-up keeps brand-named browser phrasings (`导出 Chrome 保存的密码`) inside the terminal rule.
- **Grok capability probes accepted truncated terminals, and native routes now run the preflight.** The probe body caps output at one token, so a reasoning model always finishes with `response.incomplete`. Because the Responses branch only counted `response.completed` as success, every reachable Responses endpoint was recorded as unavailable with `http_status=200`, which permanently disabled native passthrough for Codex→Grok and reported a live protocol as dead. The native branch also skipped the Grok preflight entirely, so Codex-only tool shapes (custom, namespace, `tool_search`, `additional_tools`) would have gone upstream raw; both halves are fixed together.
- **Dispatch-state reconciliation no longer runs on the request path (PR #544 by @ImogeneOctaviap794).** Reconciliation moves to a shared background pass, and a request that misses re-enters the full selection loop — including the availability wait — once that pass completes, instead of getting a single immediate re-check, so a repaired pool no longer drops the rest of a concurrent burst. Credit accounts previously only avoided *entering* a usage-window cooldown; an account already cooling down was never released, so the most natural workflow — noticing an account is rate limited and only then flipping the toggle — did nothing until the window reset. Enabling the toggle, or a balance top-up landing via the usage probe, now releases the locally derived usage cooldown, distinguished from a genuine upstream 429 by whether the penalty deadline lines up with the 7d reset instant; upstream cooldowns are left intact. The status badge deliberately keeps saying "rate limited" — the window really is exhausted — while a separate `using_credits` signal renders a compact credits icon between the status badge and the countdown, and `IsAvailable` keeps the account in rotation. Because such an account now *displays* as rate limited, both "clean rate-limited accounts" paths skip it, so a one-click cleanup can no longer delete an account that is working fine.
- **Referral invites show the remaining monthly capacity and the invites already sent.** The invite view could only send; there was no way to know how many invites were left or what happened to earlier ones, and the two upstream limits are not the same number — 10 sends per month, but only the first 3 earn rewards, so everything past the third was silently unpaid. The eligibility and tracking endpoints are now wired through, surfacing both capacities, the upstream offer copy, and the 90-day invite list with redemption status and expiry. Remaining capacities are carried as pointers so "upstream said zero" stays distinguishable from "upstream omitted the field" — only the former blocks sending.

### Fixes

- **`malicious_persistence_c2` no longer terminates a request over a bare mention of persistence — roughly 1128 false hits per day in production (by @ifThink404).** The Strict, terminal rule matched bare "persistence" / "持久化", so ordinary software-engineering text (a persistence layer, persisting a task id) was blocked outright. Strong terms (malicious persistence, C2 server, botnet, backdoor service) still match on their own; the weak wording now requires co-occurring malicious context. A pre-existing gap where a Chinese verb plus English "C2 server" went unmatched is fixed in the same change, with production-sample regression tests.
- **`operational_exploit_request` no longer fires on bare payload/poc vocabulary (by @ifThink404).** The Chinese branch matched unqualified "payload" and "poc", so ordinary developer text was terminally flagged: a git/API request payload ("使用生成的 payload 创建 pr") and the "poc" substring inside identifiers ("mattpocock/skills"). The English branch is unchanged.

Co-located user text is still scanned. The noise disappears with zero detection impact.
- **`adapter_unclassified` audits record which type was unrecognised (by @ifThink404).** The audit previously reported only that one occurred. The request envelope now carries bounded, deduplicated type names, surfaced into the audit `match_context` as `unclassified_types: <name>` — schema names only, never user content — so operators can see which new Codex type needs an explicit adapter mapping.
- **Hidden continue-thinking rounds no longer hit a reverse proxy's idle timeout (#458).** With `codex_continue_thinking_enabled` on, hidden continuation rounds forward nothing downstream while opening the next round and while that round produces no forwardable reasoning events. Behind a reverse proxy with a 60-125s idle read timeout the proxy cancels the request with 524/context-canceled mid-fold, the CLI retries the whole outer request, and every retry re-enters the fold — a reconnect loop that multiplies latency and real upstream spend. Once the fold confirms continuation, a ticker writes a standard SSE comment (`: keepalive`) every 15 seconds; parsers ignore comments but every hop's idle timer resets. The callback stays inert until the first real body byte is written, so pre-first-token error semantics (real HTTP status for early `response.failed`, account rotation) are untouched. The pass-through path starts no ticker and stays byte-identical.
- **Image job warnings are separated from errors, and upscaling no longer crops by default.** A batch that degraded but still produced images was marked succeeded with the notice written to `error_message`; the external job API returns the record verbatim, so a caller treating a non-empty `error_message` as failure reported a successful batch as failed. The notice now has its own warning field and `error_message` means the job failed (no schema change — the two share a column on disk). The external upscaler also forced `fit=cover` whenever the requested size matched exactly, overriding the operator's `IMAGE_UPSCALER_FIT` and cropping any source with a different aspect ratio, while the local backend never crops — the same request produced different images depending on whether an endpoint was configured. The default is now to fit inside the box, identical to cover when the ratios match, with cropping still available to operators who ask for it.
- **Image outputs honour the requested size, and partially successful batches survive.** The local upscaler never received the requested size and resampled to the tier long side instead: asking for 2048x2048 produced 2560x2560, and 2880x2880 produced 3840x3840 — both first-class 1:1 sizes behind the `gpt-image-2-2k`/`-4k` aliases, so the default backend inflated every square output. The target box is now resolved once and shared by both backends, and `DoUpscaleTo` lets the local path hit an exact target without cropping a mismatched aspect ratio. An undecodable upscaler response previously failed the whole job while outputs saved before it stayed on disk and in the database, already billed but unreachable behind a failed job; it is now degraded like a transport failure, and both job runners report a save-stage failure as a warning whenever earlier outputs survived.
- **Image jobs regain admission control, and timed-out jobs no longer stick in "running".** `MaxConcurrency` stopped gating image jobs: the slot used to be reserved at enqueue and held until the background job finished, which is what made it admission control, but batching moved the reservation to each upstream call — so every request was accepted and the ones that could not run turned into failed job rows instead of a synchronous 429. Reserving at enqueue again is only safe if the job's own upstream calls stop reserving a second slot for the same key, so the existing concurrency-inherited signal is passed down through the admin image calls; with `MaxConcurrency=1` the job would otherwise deadlock against itself. Job deadlines now scale with the requested output count, since a batch can issue one upstream call per output and repeat the whole batch through the JPEG fallback. Terminal status writes run on their own context — the job context is routinely past its deadline by then, so the write failed and the row stayed "running" until the next restart with the error discarded. Upscaler responses outside `image/*` are rejected, and a fallback to a per-process random signing key is logged.
- **Referral invites work again — the upstream endpoint had moved and every send was failing.** `POST /backend-api/wham/referrals/invite` now returns a route-level 404: the `wham/` prefix was dropped and the request body's single `referral_key` field was split into `program_id` + `entrypoint`, confirmed against the upstream's own 422 validation response. The client was updated to the current contract, and the send-response parser accepts both `invites[]` and `items[]` since the success payload shape is not yet observed.
- **Cloudflare bot challenges are no longer reported as "this account has no referral eligibility".** These endpoints sit behind Cloudflare bot management, where Go's default TLS fingerprint had roughly half of all requests thrown into a managed challenge — the challenge page borrows a 403, and the UI mapped every 403 to an eligibility failure. Requests now use the repository's existing uTLS Chrome fingerprint, reusing the pooled maintenance client so no HTTP/2 connections leak, with a per-account cookie jar so `__cf_bm` is reused, taking a measured 2-of-10 success rate to 12-of-12. Challenge pages are detected explicitly — the whole body must be scanned, since the markers sit past 7KB of inline SVG — and reported as retryable instead of as an eligibility verdict. The polymorphic `detail` field is parsed in both shapes, so a recipient-level rejection reports the upstream reason and the exact failed addresses rather than blaming the account.
- **The Codex invite view has its own route.** It was local component state, so a refresh dropped back to the account list, the page could not be linked, and the browser back button left the accounts page entirely. It now lives at `/accounts/invite`, matching the existing `/accounts/grok` pattern; deep-linking while the account list is still loading no longer reports "no accounts available for invites".
- **Resetting an account's quota refreshes its status and usage bars immediately.** After clicking reset, the account kept showing its old usage and status until the operator ran a connection test and refreshed by hand. The reset succeeded and a usage probe was dispatched, but only as a background goroutine — the handler returned 200 immediately while the probe (a wham round trip, normally 1-3 seconds) was still in flight, so the client refetched stale data. The manual reset now waits for the probe to land before responding, bounded at 15 seconds; the response carries `usage_refreshed` and the refreshed status so the client can schedule one late refetch if the probe timed out, and an unavailable probe returns immediately instead of blocking the request.

- **Long-running WebSocket streams are no longer killed at 120 seconds of upstream silence — and a genuinely stalled turn can no longer pin a stream forever.** The WS read path enforced a hard 120s timeout between business frames, so a long reasoning turn or a priority-queue wait that legitimately produced no incremental frames for two minutes was misjudged as a dead connection and cut off mid-response. Business-frame silence is now only a liveness checkpoint: recent inbound activity (data frames, peer pings, heartbeat pongs) proves the transport is alive, and an otherwise-silent connection gets a correlated Ping probe with a unique payload — a frame arriving mid-probe wins over probe failure via a queue-sequence guard, so no response is lost at the checkpoint boundary. The follow-up hardening closes the opposite gap the removal opened: liveness proves the transport is alive, not that upstream is still working the request, so a wedged upstream worker behind healthy heartbeats could otherwise pin the request, its read lease and the pooled connection indefinitely. Business-frame silence is now capped at 15 minutes (`CODEX_WS_MAX_TURN_SILENCE`, Go duration format, `"0"` disables), both failure paths report as timeouts in failure attribution again instead of generic transport errors, probe rescues and silence-cap kills leave attribution logs, and the never-consumed 2-minute pending-request timeout that other code cited as a backstop was retired. The probe-failure rescue branch is covered by a mutant-verified regression test.

Resets now restart the enforced windows while preserving usage history and unrelated windows, flush buffered usage logs and evict the relevant runtime caches so the reset takes effect immediately; the bulk reset-all path additionally guards against concurrent resets racing each other.
- **Overflow auto-compact summary requests are attributed to the API key that triggered them.** The experimental context-overflow auto-compaction issues an internal summarization turn; its usage previously landed unattributed. `usage_logs` gains `internal_reason` and `parent_request_id` columns (added automatically on startup) so the summary turn is billed to the originating key and linked to the request that triggered it.

## v2.6.6 - 2026-07-27

### Features

- **Requests without a Codex client fingerprint can be routed into dedicated account groups (#445, by @ekti123456).** Traffic that carries no `x-codex-*` header — third-party gateways, custom clients, anything that isn't the official CLI — can now be confined to a chosen set of account groups, keeping it off the accounts that serve real Codex sessions. Two follow-ups make the isolation actually hold: an **empty allowed-group list on a key** (how most keys are configured) previously aborted the split entirely, so the split group served the no-fingerprint traffic it was meant for *and* kept taking Codex traffic — it now means "every group except the split ones"; and the filter was only wired into the five conversation entry points while store-level authorization had been widened everywhere, so **image requests leaked in both directions** (landing on split accounts regardless of fingerprint, and no-fingerprint image traffic never being confined) — image selection (preferred tier, fallback tier, and the wait-for-account path) plus the alpha search endpoint now apply the same filter. The UI hint spells out the empty-list behavior and, importantly, that the fingerprint is a **client trait any downstream caller can set itself**, not a boundary it is kept out by.
- **The Grok OAuth `client_id` is configurable — as an environment variable and as a hot-applied system setting (#448, by @Story19240).** The official Grok CLI id was a hard-coded constant across eight call sites (browser authorize/exchange, refresh, the SSO→Build conversion chain, the manual device flow); it is now a single configurable value: `GROK_OAUTH_CLIENT_ID` (reusing the existing `grokEnv` convention) or `grok_config.oauth_client_id`, editable from the new **Grok section** of the settings page. When the env var is set, the settings API reports the override alongside the effective value and the form disables the input and names the value actually in use, so nobody edits a field that cannot take effect. Since a `client_id` ends up in the authorization URL and the token form, values with whitespace or control characters, or longer than 128 bytes, are rejected with a `400` rather than silently normalized to empty — a silent fallback would look like a successful save while the default was still in use. Existing accounts are untouched: refresh uses the `client_id` stored in each account's own credentials, so this only affects authorizations created from now on.

### Fixes

- **HTTP/2 connections and goroutines no longer leak without bound in `utls_chrome` transport mode (#446).** The self-managed uTLS transport never reclaimed its connections: a reporter saw **45k ESTABLISHED connections and 45k goroutines after ~39h with only 3 active requests**, growing until the host ran out of memory. Four independent defects combined. `IdleConnTimeout` was never set on the `http2.Transport` — `NewClientConn` only installs the idle timer when the timeout is non-zero, so `closeIfIdle` never fired and every connection's `readLoop` goroutine pinned its socket and buffers forever, unreachable for GC (now 90s, matching the standard transport, which backstops every other reclaim path). `CloseIdleConnections()` tested `!CanTakeNewRequest()`, but healthy idle HTTP/2 connections answer `true` — the condition skipped precisely the connections that needed reclaiming; it now reclaims connections with no in-flight streams, unlinking under the lock and closing outside it, with a short grace window so a connection handed out but not yet used isn't closed underneath its caller. The pooled-client eviction path called `client.CloseIdleConnections()`, a no-op for uTLS, so every TTL eviction leaked a connection — this hit normal `/responses` traffic, not just auxiliary calls — and now dispatches by transport type. Finally, wham usage/reset-credits, the Codex models manifest, alpha search and subscription sync each built a throwaway `http.Client` per call (constantly, given background probes and clients polling `/models`); they now share pooled clients keyed by purpose + account + proxy + transport mode, with maintenance clients kept separate from the `/responses` pool so a failing background probe can't recycle live request connections. In-flight streams are drained by graceful shutdown rather than a hard close, capped by the new `utls_shutdown_timeout_minutes` setting (default 30 min, range 1–240, out-of-range clamps to the default) since a single streaming turn can exceed 10 minutes (#287). Verified against a live PostgreSQL deployment in `utls_chrome` mode: 210 `/models` requests (41 reaching upstream) left zero upstream `:443` connections after settling, goroutines returned to the 29–30 baseline, and streaming responses completed intact.
- **Usage-log batching can no longer stall on one unwritable row, drop the buffer on shutdown, or grow until OOM (#444, by @ImogeneOctaviap794).** The batched writer landed with three failure modes that all cost money rather than just dashboard data — the same transaction advances the API key scope counters and `api_keys.quota_used`, and budget enforcement reads exactly those persisted counters, so a stuck writer leaves budgeted keys below their limit forever. A failed batch insert was always requeued at the head of the buffer, so a row that can *never* be written (SQLSTATE class 22/23 — overlong value, invalid UTF-8, numeric overflow, constraint violation) stalled the writer permanently; failures are now classified, transient errors (connection loss, timeout, deadlock) requeue exactly as before while data errors **bisect the batch**, write everything writable and drop only the offending rows, never handing back rows already committed. `Close()` called `flushLogs()` after stopping the background flusher, but `flushLogs()` had become batch-at-a-time and relied on that flusher to drain the rest — so everything past the first batch was dropped on graceful shutdown, worst exactly in the high-RPM case the batching targets; it now drains via `FlushUsageLogs()`. Overlong values are clamped to their column width by rune before entering the buffer (widening `varchar(20)` to `varchar(100)` raises the ceiling but doesn't remove the failure mode — `reasoning_effort` / `service_tier` come straight from the request body or the upstream response). And the unbounded buffer is now capped at 20000 entries, dropping oldest first, with the dropped total surfaced on the runtime status page next to the buffer gauge.
- **Grok batch import stays usable at the raised 5000-file cap (#447, by @Futureppo).** The caps went from 500 files / 200 refresh tokens to 5000 without touching the two things that made the old numbers work. The file import ran its whole sequential insert loop under a fixed 60s deadline, so the per-file budget *shrank* as the batch grew — 120ms at the old cap, 12ms at 5000 — and any database hiccup expired the context partway through, reporting `context deadline exceeded` for every remaining file; the deadline now scales as 30s + 100ms per file, capped at 10 minutes so one oversized request can't hold a connection open indefinitely. Wall-clock was the other half: a single request inserting thousands of rows, or refreshing thousands of tokens six at a time, runs far longer than a browser or reverse proxy will wait, with no progress and no way to tell what landed — the credential-file and refresh-token imports are now submitted in **chunks of 200**, merging per-chunk results, showing which chunk is running, and keeping finished chunks visible if a later one fails.
- **Grok requests stop 400-ing at the context-compaction turn (#450).** Codex CLI's compaction turn emits `tools:[]` together with `tool_choice:"auto"`; the xAI upstream hard-validates that combination and answers `400 invalid-argument "A tool_choice was set on the request but no tools were specified."`, while the Codex/ChatGPT upstream tolerates the identical body — so every long Grok session broke at its compaction point, and a `400` isn't retried. The Grok sanitize path now drops `tool_choice` when `tools` is absent or empty (with no tools declared the field has no meaning, so removing it is semantically free). ## v2.6.5 - 2026-07-25

### Features

- **Per-key usage budgets scoped to individual account groups and accounts (#439).** A key allowed to reach both a premium group and a cheap relay group can now be capped on the premium one alone and fall through to the cheap one once that cap is hit. Budgets are enforced as **scheduling candidate filters** rather than an entry-side reject — the whole point is to keep serving from the other scopes — hooked into the existing `auth.AccountFilter`, which covers the fast scheduler, the slow loop, lazy mode and sticky session reuse in one place. `on_exhausted=skip` (the default) drops that scope's accounts from the request's candidate pool and, when the pool ends up empty, answers `429` naming the exhausted scope instead of the vague `503 no available account`; `on_exhausted=reject` fails the whole key as soon as any scope runs out. Three independent dimensions: **sliding windows** (5h/1d/7d/30d over cost / tokens / requests), **cumulative quotas** that never decay and need an explicit reset, and a **per-scope concurrency cap**. Metering uses `user_billed`, matching the existing key-level cost limits, and unpriced models bill `$0`, which is why the token and request dimensions exist at all. Window data comes from one per-account `usage_logs` aggregation per window (cached 60s, so the cost is independent of how many scopes a key configures) plus an in-process delta so a budget that just ran out isn't overshot for a whole cache cycle; with Redis the delta is also published to per-minute buckets for sibling instances, merging only buckets strictly newer than the snapshot minute since the straddling bucket would double count. Group attribution is computed in Go against live group membership, so moving an account between groups takes effect immediately without denormalizing `group_id` into `usage_logs`. Cumulative quotas are a separate data source — `api_key_scope_counters` is incremented inside the same transaction as the usage-log batch, so the verdict lags one flush exactly like `api_keys.quota_used`, with group rows resolved by a SQL join on `account_group_members` and only keys whose persisted limits declare a cumulative quota accounted for; limits stay in the limits JSON while used amounts live in the table, so the config has exactly one copy. Per-scope concurrency is deliberately a **soft** cap: the filter check and the slot acquisition race, so a burst can exceed it by one or two, and making it hard would mean reworking the retry structure of all six forwarding paths — slots carry a deadline so a missed release self-heals instead of wedging a scope forever, and concurrency ignores `on_exhausted=reject` because transient contention shouldn't fail a request outright. Exhausted scopes are counted per affected request, surfaced in the edit drawer and logged (throttled), since a request silently downgraded to a worse account otherwise reads as an unexplained quality drop. - **In-flight requests are protected from WebSocket pool maintenance — no more same-second batches of 598 on unstable networks (#436).** The v2.6.0 trailing-metadata-frame fix made pooled WS connections genuinely long-lived for the first time, which exposed two latent maintenance paths that could kill connections *with requests still in flight*: a failed 30s heartbeat ping called `session.Close()`, cancelling every pending request on that session at once (under a network stall ≥10s, every pooled connection's heartbeat fails in the same window — the reporter's "batches of 598 with identical timestamps"), and the 30s `evictExpired` sweep closed idle-expired connections/sessions without checking `PendingCount()`, so a long-thinking turn or lost pongs got an active connection reaped mid-stream. v2.5.9 was immune only by accident: the trailing-frame bug killed every connection after each turn, so these paths never ran against live traffic. The silent-retry window also widens: stream-commit decisions now use a strict "first real content frame" tracker (decoupled from the loose `first_token_mode` stats setting, which counted structural frames like `response.output_item.added` as first token), and pre-content structural frames stay buffered — a break during the thinking-start phase, exactly where the #436 connection kills used to land, is now retried on another account with the downstream none the wiser. - **Inbound request bodies are decompressed per `Content-Encoding` — zstd bodies from new Codex clients parse correctly (#373/#388).** Codex Desktop/CLI 0.144.2+ under a `requires_openai_auth` + bearer-token configuration compresses the `/v1/responses` body with zstd; the gateway never decompressed inbound bodies, so the compressed bytes were parsed as plaintext JSON — a large body failed local validation with "Field 'model' is required", while a small one could slip past validation on literal residue inside the zstd frame and leak compressed bytes upstream ("The 'None' model is not supported"). - **Compact model-mapping regression: synthesized aliases no longer hijack generic wildcard rules, and mapping targets are stripped of `-openai-compact` before reaching the upstream (#350 regression).** v2.5.0's compact mapping resolves the endpoint-qualified `<model>-openai-compact` alias before the base model, but the alias *synthesized* for clients that sent a plain base name participated in all rule matching, with three fallouts. (1) Rules keyed on the suffixed name — which operators had copied from relay-side compact route markers (e.g. `gpt-5.6-sol-openai-compact` in a channel's model list) and which were dead letters before v2.5.0 because the suffix was stripped before matching — suddenly activated and forwarded the suffixed name verbatim upstream; relays fail to resolve it as a literal model, and compaction died with `stream disconnected before completion: stream closed before response.completed`. (2) Generic wildcard rules (`gpt-*`, `*`) matched the synthesized alias and outranked the base model's exact rule. (3) An identity suffixed→suffixed rule could knock an account that only lists the suffixed marker out of the compact pool entirely (503 no available account). Now a synthesized alias only matches rules explicitly keyed with the `-openai-compact` suffix (including `*-openai-compact` wildcards); any matched mapping target has the suffix stripped before entering the upstream body — the upstream call is always `/v1/responses/compact`, where the alias convention never applies; and the compact account filter and per-attempt rewrite share the same resolver. Verified via an A/B scenario matrix against the pre-#350 build: every configuration is restored to its pre-v2.5.0 upstream behavior, while v2.5.0's intended feature — suffixed-key rules that apply only to compaction — keeps working. Usage stats also now display the base model for suffixed requests: a bare suffix strip no longer renders as a mapping arrow (`gpt-5.6-sol-openai-compact → gpt-5.6-sol` simply shows as `gpt-5.6-sol`), which also keeps pricing lookups on the clean base name.

It is currently a soft signal — plain CLI / non-macOS clients legitimately never send it — so the proxy takes the only correct stance: forward the header verbatim when a downstream real Codex client supplies it (on both the HTTP and WebSocket OAuth Codex paths, never on the API-key relay path), and **never fabricate it** (a forged token fails Apple verification and is a worse fingerprint than absence). ### Fixes

- **Idle upstream WebSocket connections are no longer misjudged alive — fixing pre-first-token retries, dropped streams, and 598s (#349).** In forced-WS mode a connection returned to the pool had no reader, so gorilla/websocket never processed the upstream's keepalive `Ping`/`Pong`/`Close` control frames while idle. The upstream declared the connection dead (`close 1011 keepalive ping timeout`) and queued a Close frame, but the local state stayed `Connected` and the write-only Ping probe still "succeeded" — so the dead connection was handed to the next request, whose first read immediately hit the queued Close. That surfaced as slow first tokens (silent retries), and consecutive dead-connection reuse exhausted retries into `status 598` / "stream disconnected before completion" (609 keepalive-timeouts in a single reported instance). Each physical connection now runs a **permanent read pump** — the sole reader — so control frames are handled in real time (Ping is auto-answered), a queued Close or read error flips connection state immediately, and business frames are delivered to the request consumer through a bounded queue with per-request leases. The liveness probe no longer writes a Ping (which is exactly what produced the false positive): it trusts the pump's real-time state and only checks lease/queue cleanliness, and a connection with recent inbound activity skips the ping-pong roundtrip entirely so a hot reuse doesn't pay an extra upstream RTT. Verified end-to-end (PG+Redis, `gpt-5.6-sol` reasoning `max`, `/v1/responses`) that 75s/150s idle-reuse windows and concurrent load succeed with a stable ~0.3s first event and zero keepalive-timeouts.
- **WebSocket connections rotate at 50 minutes to dodge the upstream 60-minute lifetime cap (#346).** The upstream enforces a 60-minute per-connection lifetime; past it, `response.create` is rejected with `websocket_connection_limit_reached` while the Ping probe keeps succeeding, so age can't be inferred from probing. Connections are now proactively rotated — destroyed while idle — at 50 minutes (10-minute headroom so in-flight streams finish), and the lifetime error frame marks the connection dead so it can't keep poisoning subsequent requests, including continuation-affinity ones.
- **Continue-thinking no longer inflates the context window until it overflows (#353).** The continue-thinking fold stacked **every** round's reasoning (including the account-bound `encrypted_content`) into the folded response's `output` — a single response could carry N reasoning blocks instead of the normal one. A client echoing that N× history back on the next turn overflowed the model's context window (`400 context_length_exceeded` on the first round), and on cross-account replay each of the N encrypted blobs was rejected by the newly scheduled account, spamming the `encrypted_content` strip-and-retry path. The folded downstream output now keeps full `encrypted_content` only for the **final** round and strips it from earlier rounds (their summary text is retained; those rounds' encrypted context already did its job during folding and produced the final answer). The change touches only the client-facing output — the `replayTail` sent upstream for same-account continuation is unchanged, so the folding mechanism itself is unaffected. `CODEX_CONTINUE_KEEP_ALL_ENCRYPTED=1` restores the old behavior. A single response that natively emits multiple reasoning blocks (no folding) keeps all of them.
- **`gpt-5.6-sol` / `gpt-5.6-terra` / `gpt-5.6-luna` are billed at their distinct official prices (#344).** The three gpt-5.6 variants carry different official rates; they were all folding onto gpt-5.4's price. Each now bills separately (sol `$5/$30` with cache-write, terra `$2.5/$15`, luna `$1/$6`), with priority tiers derived as the standard 2× where the upstream doesn't publish an explicit one.
- **Model mapping now applies to remote compaction requests (#350).** Aggregating clients append an `-openai-compact` suffix to compact requests, but the suffix was stripped **before** model mapping ran, so a mapping configured against the compact alias never matched; and body-signal compact promotion mapped the model twice. Compact requests now resolve the endpoint-qualified alias first (falling back to suffix-strip + normal mapping), map exactly once, and account routing accepts the synthesized compact alias so an account isn't wrongly judged unable to serve it. Billing is unaffected (it follows the effective model).
- **Compaction history is distinguished from a compaction trigger (#347).** The body-signal detector scanned `input` recursively and treated durable `compaction` / `context_compaction` history items (which carry `encrypted_content` and belong in later turns) as new compaction triggers — polluting usage stats with `compact=true` and promoting ordinary requests to the compact chain on relay-only pools (returning compaction output instead of a normal message). Only a bare top-level `compaction_trigger` item now counts as a trigger; durable history items ride through the normal `/v1/responses` path.
- **Codex client identity completed for restricted relays (#351).** Some third-party Responses relays that only accept the official Codex client also validate the request body's `client_metadata.x-codex-installation-id`; a UA-only rewrite was rejected with `403 codex_access_restricted`. A per-account `codex_client_metadata_mode` (`auto` / `always` / `off`, default `auto`) now injects a deterministic (UUIDv5, stable across restarts) installation id and retries once, but **only** on that exact `403 + codex_access_restricted`, then remembers the relay's requirement keyed by account + base URL. Default `auto` leaves the first request identical to before, so ordinary Codex accounts and the compact path are unaffected.
- **Responses outcomes can be the authority on account availability (#343).** New opt-in `ignore_usage_limit_status` (global, with per-account override): when enabled, 5h/7d usage percentages become display-only, an account isn't locally cooled down by a usage snapshot alone, and availability is decided by real Responses results — a genuine 429 still cools the account, and a confirmed Responses success clears that usage cooldown (WHAM is demoted to metadata and can't clear it). Accounts that ignore usage limits are also skipped by the full-usage auto-cleaner, so a snapshot that's now merely informational can't soft-delete them.
- **Anthropic empty content-block fields are preserved (#339).** Strict Anthropic-stream clients (e.g. OpenCode) require `content_block.thinking` / `content_block.text` to be a string even when empty, but Go's `omitempty` dropped `thinking: ""` / `text: ""` from `content_block_start`, so the client rejected the stream with `expected string, received undefined` before any delta arrived. A custom marshaler now keeps the empty field for the matching block type while leaving `tool_use` blocks unaffected.
- **Batch account tag/group edit is per-field opt-in (#348).** The batch metadata editor used to union all selected accounts' tags and groups and write them back to every account, so changing one field silently overwrote the other. Each field now has an independent switch: a disabled field keeps each account's current value (it isn't sent), and only an enabled field is uniformly applied (empty clears it). Both switches off disables save.
- **SQLite transactions use immediate locking, eliminating concurrent-write "database is locked" (#353-adjacent).** A deferred transaction takes a read lock first and only upgrades to a write lock at the UPDATE, and that upgrade returns `SQLITE_BUSY` immediately — `busy_timeout` doesn't cover lock upgrades. The DSN now sets `_txlock=immediate` so a write transaction acquires the write lock at `BEGIN` and concurrent writers queue on `busy_timeout` instead of erroring; this also removes a rare `database is locked (517)` flake between an account update and its async event insert.
- **WebSocket bad-handshake errors carry upstream detail.** A failed WS handshake now surfaces the upstream HTTP status, key headers, and raw JSON body instead of a bare `websocket handshake failed: <code>`, so connection-test failures on relay/OAuth accounts are diagnosable.

### Fixes

- **Streaming requests that fail before the first token now return real HTTP errors instead of 200 (#318, reported and first-fixed by @JrCx7scC).** When the upstream terminated a stream with `response.failed` (e.g. `context_length_exceeded`) before any token, codex2api wrapped the failure into a 200 SSE stream (plus `[DONE]` on the chat path), so billing middle layers treating codex2api as an upstream saw a normal-looking success with no usage and billed their users by *estimated input tokens* — "upstream rejected with 0 output, user billed for the full input". The original PR's direction was right but didn't survive the wire: the post-loop flush committed the 200 header before the error JSON could be sent (gin's `Flush()` calls `WriteHeaderNow()` even on an empty buffer), so the fix additionally guards the epilogue flush on "wrote any body", overrides the pre-set SSE Content-Type, and gates the error return on an explicit abort flag. Applied across Responses/ChatCompletions streaming, the OpenAI Responses direct branch, and inbound WebSocket — where there is no HTTP status to fix, so non-retryable pre-first-token failures now send a structured `error` frame and close with a semantic close code (429→1013, other 4xx→1008, 5xx→1011) instead of relaying the raw failure frame and ending the turn as if it succeeded. Retryable failures keep the existing silent-retry/relay contract.
- **wham 401 no longer unilaterally bans an account — the `/responses` probe is the final arbiter (#328).** codex_at (bare AT import) accounts can be permanently 401 on the wham endpoint (token missing a workspace claim) while real `/responses` traffic works fine; the usage probe treated that 401 as dead credentials and put the account into a 24h unauthorized cooldown — re-banning it after every manual reset, or flapping banned/unbanned every probe round when fallback probing was on. A wham 401 is now a sentinel: no failure report, no ban. When fallback is available the `/responses` probe delivers the auth verdict (200 recovers / 401 bans); in wham-only mode the 401 is just logged, leaving genuinely dead tokens to be cooled down by real-traffic 401s.
- **Duplicate-account merge race could soft-delete both accounts.** After a merge, the async probe reload on the surviving account could trigger a reverse merge before the losing row was soft-deleted — the reverse pass merged old→new, then the outer pass soft-deleted the new row too, losing the account entirely (reproduced deterministically in CI where the fake probe returns instantly). Merges are now serialized under a mutex and the losing row is soft-deleted before the probe reload, so concurrent or recursive merges always see each other's results.
- **Online update hardening (#327, #329).** After an in-place update the restart re-exec could still launch the *old* binary — `os.Executable()` resolves `/proc/self/exe`, which after the atomic swap points at the deleted old inode; restart now execs the explicit new binary path. The frontend no longer caches the whole update-info blob (a stale `has_update=true` survived the update and kept showing "new version available" when current == latest); only the remote release fields are cached and the comparison is recomputed against the running bundle version on every check. The update/restart UI also gains client-side timeouts and a "refresh manually" hint when the restarted process doesn't answer within 90s.
- **Usage stats "source account" column shows email again.** A v2.4.5 frontend change made the account *name* take precedence, so unnamed AT-imported accounts all rendered as their placeholder name (`at-account-1`) instead of their email identity; the order is restored to email → name → ID on both the usage and operations views.

- **Reset-credit expiry details in the account usage dialog (#322).** The "manual quota reset" section now fetches the per-credit breakdown from the upstream's zero-cost reset-credits list endpoint and shows each credit's expiry time, sorted soonest-first with credits expiring within 7 days highlighted — so you can see not just how many resets are left but when each one becomes worthless, and burn the soonest-expiring ones first. The authoritative available count from the detail endpoint also recalibrates the locally cached number. Detail fetch failures degrade gracefully: the count and the reset button keep working, only the expiry list shows an "unavailable" hint.
- **Content-derived session seeds: multiple users behind one shared API key now stick to accounts per-conversation.** When a single API key is used as a channel for a whole downstream site, sessionless requests all collapsed onto the same key-derived affinity key — every user squeezed onto one upstream account and account switching was all-or-nothing per key. A content-derived seed (sha256 over conversation-stable fields: model + instructions + tools + system/developer + first user message) now slots in between explicit session signals and the per-key fallback, so each conversation converges onto its own sticky account and the pool load spreads out. ### Fixes

- **Forced-WS + shared single API key no longer bleeds context across users.** With `codex_force_websocket` on and one API key shared by multiple end users, user 2's turn could get stitched onto user 1's conversation: the reused stateless connection's handshake headers (`Session_id`/`Conversation_id`) were frozen to the *first* request's cache key and never updated, so an upstream that keeps per-connection conversation state saw every later user under the first user's session identity (same family as #268/#308). Stateless reused connections now send *no* session identity in the handshake at all — per-request isolation rides entirely on the per-request `prompt_cache_key` in the frame body; explicit-session and per-api-key modes are unchanged. A `CODEX_WS_STATELESS_ONESHOT=1` escape hatch disables slot reuse entirely (one connection per request, hard isolation, at the cost of per-request handshakes). Continuation affinity is also fixed: `previous_response_id` context lives only inside the connection that produced the response, so continuation requests now return to their original connection (response→connection bindings with TTL and a 4096 cap, guarded by account + API-key ownership + connection-pointer checks) instead of intermittently hitting "previous response not found" on a random slot.
- **`previous_response_id` context cache is isolated per downstream API key.** The response cache was keyed globally by `response_id` and expansion never checked ownership, so any request presenting (guessing, or accidentally reusing) someone else's response id would get that user's full conversation items injected into its input — a cross-key context leak. Cache entries are now namespaced by owner (`key:<id>`/anon) across all three write/expand paths (HTTP streaming + non-streaming, WS-native ingress, translator inline expansion); an owner mismatch is treated as a plain cache miss.
- **DB failures and upstream account 401s are no longer misreported as client 401s (#323).** Two layers of "server/account-side trouble" surfaced to clients as "your API key is invalid": (1) API-key resolution collapsed "key not found" and "DB failure" (connection exhaustion, timeouts) into the same result, so under load a PG "too many clients" turned into 401 `invalid_api_key` — resolution is now three-state, real DB errors return 503 and skip the `AUTH_FAILED` audit log so credential-attack alerting stays clean; (2) an upstream account's revoked OAuth token, after retries were exhausted, passed through as a raw 401 — non-`missing_scope` upstream 401s are now rewritten to a 503 pool-level error (`account_pool_unauthorized`), clearly distinct from client auth failure. Account-side handling was already correct (401 accounts get banned + cooled down); this fixes only the status-code leak to clients.
- **Free/team monthly-window accounts label their long usage window "30d" instead of "7d" (#324).** v2.4.4 taught the backend to recognize monthly (~30 day) rate-limit windows, but the frontend still hard-coded the long-window label as "7d" — misleading for free and team accounts whose long window really is a month. Also fixes the 7d billed-cost window start, which was hard-coded to `reset − 7 days`: for a monthly window that start date landed in the future, so `billed_7d` was stuck at 0.

## Features

- **Credit quota support (#141).** Added `credit_enabled` and `credit_skip_usage_window` flags to the accounts table. Credit-marked accounts skip usage-window penalties in the scheduler. Managed via `PATCH /api/admin/accounts/:id/credit`.

- **Scheduler mode (#133).** Added `scheduler_mode` system setting with two modes: `round_robin` (default, weighted by dispatch score) and `remaining_quota` (prioritize accounts with lowest usage percent). Configurable from Admin Settings page.

- **5h/7d windowed USD cost display.** Replaced the single total-cost column with a windowed billing view. Each account now shows `billed_5h` and `billed_7d` fields aligned with the account's usage-reset boundaries. This reflects actual spending, not estimated token costs.

- **Image-to-image in Image Studio (#135, #136).** The admin Image Studio now supports image-to-image generation via `POST /api/admin/images/edit-jobs`, accepting reference image URLs or data URIs. Added text-to-image and image-to-image tabs in the frontend.

- **Billing model expansion.** Added pricing for gpt-5.5-pro and gpt-5.4-pro families. Implemented long context (>272K tokens) premium pricing for gpt-5.5, gpt-5.5-pro, gpt-5.4, gpt-5.4-pro with automatic detection. Fixed gpt-4o and gpt-4o-mini cache-read pricing.

## Security

- **SQLite default binds to localhost.** SQLite compose files (`docker-compose.sqlite.yml`, `docker-compose.sqlite.local.yml`) now bind ports to `127.0.0.1` by default. Previously they bound to `0.0.0.0`, exposing the service on all interfaces. Standard (PostgreSQL) compose files retain the `0.0.0.0` default.

- **BIND_HOST env var.** Added `BIND_HOST` environment variable support to control the HTTP listen address across all deployment modes. Documented in `.env.example`, `.env.sqlite.example`, and `CONFIGURATION.md`.

## Breaking Changes

- **SQLite compose port binding.** SQLite deployments upgrading from a previous version that relied on external access via the default compose configuration must now explicitly set `BIND_HOST=0.0.0.0` in `.env` or override the port binding in the compose file. All other behavior remains backwards-compatible.
